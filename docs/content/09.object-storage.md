title: Object storage

Object storage is where files go. User uploads, generated PDFs, exports, backups your application makes itself: anything you would once have written to disk and then regretted when the container restarted.

Buckets are S3-compatible, so the SDK you already use works unchanged. Private by default, connected to a service without handling credentials, and switchable to a public CDN-backed URL when the files are meant to be seen.

## Provisioning

On the project canvas, click **Create** and choose **Bucket**. Give it a name between 2 and 16 characters and confirm. It is ready straight away.

A bucket belongs to one [environment](/environments), so development and production keep separate files under separate credentials. An environment can hold up to 10 buckets.

## Connect

The way to give a service access is a [dynamic variable](/variables#dynamic-variables). Open the service's **Variables** tab, click the link icon in the value field, and pick from the bucket's group. A bucket exposes five values:

| Variable | What it is |
| --- | --- |
| `bucket` | The bucket name to address in API calls |
| `endpoint` | The S3 endpoint to point your client at |
| `region` | The region the bucket lives in |
| `accessKeyId` | Access key, scoped to this bucket |
| `secretAccessKey` | Secret key, scoped to this bucket |

Name them whatever your library expects. The [quickstart](/quickstart) wires them up as `S3_BUCKET`, `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY`.

The credentials are scoped to the single bucket they belong to. A service holding them cannot read, write or even see anything else in the workspace, so wiring one service to two buckets means two sets of variables rather than one set that opens both.

The bucket's **Connect** tab shows the same values, along with ready-made snippets for the AWS CLI, rclone, Node and Python, so you can point a local tool at the bucket without assembling the config yourself.

::note
Use path-style addressing in your client if it offers the choice. Virtual-host style, where the bucket name becomes part of the hostname, is not supported.
::

## Public read

Buckets are private. Objects are reachable only with the credentials, which is what you want for anything belonging to a particular user.

For files meant to be served to everyone, avatars, product images, downloads, open the **Connect** tab and switch **Public read** on. The bucket gets a public URL served from a CDN, and objects become readable by anyone with the link. The dashboard shows the URL once it is issued.

Public read is exactly that: read. Writing still requires the credentials, so your service keeps control of what goes in while the internet only gets to fetch what is already there. Switching it back off takes effect on the origin immediately, though anything already cached at the edge can outlive the change.

## Files

The **Files** tab is a browser for the bucket. It lists objects and folders, walks into prefixes, and lets you upload, download and delete without a client.

It is genuinely useful for checking that an upload landed where you expected, for pulling a file out to look at, and for seeding a development bucket with a handful of objects. It is not a transfer tool: for bulk work, use the credentials with the AWS CLI or rclone.

Uploads and downloads here go straight between your browser and the bucket using short-lived signed URLs, so files do not travel through the platform.

## Deleting a bucket

Deleting a bucket destroys its contents and its credentials. There is no restore and no retention window, so a service still holding those variables will start failing on its next request.

## Under the hood

Buckets are provisioned on S3-compatible object storage hosted in Europe, with a set of credentials minted per bucket and stored as a Kubernetes Secret in your environment's namespace. Nothing about that is Lucity-specific: an [ejected](/eject) project keeps its buckets and its credentials exactly as they are.

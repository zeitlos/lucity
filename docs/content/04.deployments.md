A deployment is everything that happens between a commit and a running container: Lucity builds an image from your source, points the service at that image, and replaces the running instances with new ones.

You can watch all of it from the **Deployments** tab of a service, which lists every deployment with its current state and its logs.

## The four steps

Every deployment moves through the same four steps, and the dashboard shows them in order:

| Step | What happens |
| --- | --- |
| **Build** | Your source is turned into a container image. See [builds](/builds) for what that involves. |
| **Secrets** | The commit is scanned for leaked credentials. |
| **Deploy** | Once the build succeeds, the service is pointed at the new image. |
| **Rollout** | The new instances start and the old ones are retired. |

Build and Secrets run at the same time. The secret scan never blocks a deployment: it reports what it found and the deploy carries on regardless. Findings are still worth acting on, because a credential that reached git history stays there until you rotate it.

Deploy waits for the build. If the build fails, the deploy stops and nothing changes, so the version that was already running keeps running. The same is true of every failure before the rollout starts: a broken deployment cannot take down a working service.

A build gets 30 minutes and is not retried. If it runs out of time, the deployment fails and you try again.

## Triggering a deployment

There are different ways to start a deployment.

Each service tracks one branch, set under **Settings** → **Source**. Unless you say otherwise, a deployment builds the latest commit on that branch.

::::tabs

:::tabs-item{label="Dashboard"}
Open the service, go to the **Deployments** tab, and click **Deploy**. That builds the latest commit on the tracked branch, and the dashboard offers no way to pick a different one, so change the tracked branch first if you need another.

Each of the four steps has its own logs, streaming while the step runs, so you can watch a build compile and a rollout come up without leaving the panel.
:::

:::tabs-item{label="Git push"}
Every push to the tracked branch deploys the service. There is no workflow file and nothing to configure: this is auto-deploy, and services created in the development environment start with it switched on. You can toggle it under **Settings** → **Deploy**. Pushes to any other branch are ignored.

One push deploys every service that builds from that repository and tracks that branch with auto-deploy enabled, so a single commit can roll out several services at once. In a monorepo that is usually the point.
:::

:::tabs-item{label="CLI"}
Install the CLI and sign in first: see [CLI](/cli) for both.

```bash
lucity deploy myproject/production/web --ref main --wait --timeout 30m
```

Only the service is required. The rest are optional:

- `--ref` builds a specific commit, branch or tag instead of the tracked branch. It can be anything in the repository, not just something on the branch the service tracks.
- `--wait` blocks until the deployment is live or failed, and exits non-zero on failure, which is what makes it usable in a script. Without it the command returns as soon as the deployment has started.
- `--timeout` caps that wait. It defaults to 20 minutes and only applies with `--wait`.

See the [deploy command reference](/cli#deploy) for the full list.

To check the status of a service's current deployment:

```bash
lucity status myproject/production/web
```

That exits non-zero when the rollout is failed or degraded, so a pipeline can gate on it.

In CI, set `LUCITY_API_TOKEN` to a workspace API token instead of signing in interactively. The CLI picks it up from the environment.
:::

:::tabs-item{label="GitHub Actions"}
Lucity can deploy from a GitHub Actions workflow without you configuring a token anywhere, which is useful when the deploy should wait for something else first, such as a test suite. Turn on **CI Deploys** for the service under **Settings** → **Deploy**, then give the job an OIDC identity:

```yaml
name: Deploy
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    permissions:
      id-token: write
    steps:
      - name: Install the Lucity CLI
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          gh release download --repo zeitlos/lucity \
            --pattern 'lucity_*_linux_amd64.tar.gz' --output - | tar xz
          sudo install lucity /usr/local/bin/lucity

      - name: Deploy
        run: lucity deploy myproject/production/web --ref "$GITHUB_SHA" --wait
```

The `id-token: write` permission is what makes this keyless. The CLI exchanges the job's OIDC token for a short-lived session that can only deploy services built from that same repository with CI deploys enabled.
:::

:::tabs-item{label="API"}
To deploy through the [GraphQL API](/api) you need a workspace API token, which you create in the dashboard. Deploying is then a single mutation:

```bash
curl https://lucity.cloud/graphql \
  -H "Authorization: Bearer $LUCITY_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"query":"mutation { deploy(service: \"acme/myproject/production/web\") { id status } }"}'
```

The service id starts with the workspace here, because an API token is not bound to one project. Pass `gitRef` alongside `service` to build something other than the tracked branch.
:::

## Configuration changes

Not every change needs a new image. Editing [variables](/variables), CPU and memory, the port, the start command, the health check or a volume mount reuses the image the service is already running, and applies within seconds. The new instance starts, passes its health check, and takes over before the old one goes away, so a running service does not go dark while you change it. The exception is a service with a volume attached, which [stops before the replacement starts](/volumes#volumes-and-rollouts).

Changing the replica count is the one change that is not a rollout at all. Existing instances keep serving and new ones simply join them.

## How a rollout works

The rollout is the part where running containers are replaced, and it is arranged so that the service keeps answering throughout.

A new instance starts alongside the old one and receives no traffic until its [health check](/services#health-checks) passes. Once it does, the old instance is taken out of rotation and given ten seconds to finish requests that are already in flight before it is asked to shut down. The whole shutdown has a 30 second budget, so roughly 20 seconds are left for your process to exit on its own before it is killed. That is why [handling the shutdown signal](/services#shutting-down) matters if you care about the last few requests.

The count never dips below what you asked for. Lucity adds an instance before removing one, rather than the other way around, so a single-replica service is covered too.

Two cases work differently:

- **A service with a [volume](/volumes)** cannot overlap, because the disk is still attached to the instance being replaced. It stops first and starts again, which means [a short gap on every deploy](/volumes#volumes-and-rollouts).
- **A service with no port** has nothing to health check, so a new instance counts as ready as soon as its container is up.

## When a rollout fails

If the new instance never becomes healthy, the old one keeps serving and the deployment is marked failed. Nothing is lost and there is no rush: you can take as long as you need to work out what went wrong.

The deployment shows a reason, which is usually one of these:

| Reason | What it usually means |
| --- | --- |
| Crash loop | The container starts and exits repeatedly. The exit code is shown with it, and the [logs](/logs) have the rest. |
| Out of memory | The container exceeded its memory limit. Raise it, or find out what is holding the memory. |
| Image pull failed | The image could not be fetched. Most common on services built from a public image reference that no longer resolves. |
| Config error | The container could not be created from its configuration at all. |
| Quota exceeded | The environment ran out of its [resource budget](/environments#resource-quotas). |
| Unschedulable | There is no capacity to place the instance right now. |
| Not ready | The container runs fine but the health check never passes. |
| Deadline exceeded | The rollout made no progress within the time allowed. |

A deployment is **degraded** when some of its new instances came up and others did not, and **failed** when none of them did.

The service is a separate reading, and usually the one you care about. While the previous version is still serving, a service with a failed deployment shows as **Degraded**: your users are fine, the new version is not. It only shows as **Failed** once nothing healthy is left, which happens on a first deployment that never worked, or on a service whose old instance had to be stopped before the new one could start, such as one with a [volume](/volumes#volumes-and-rollouts) attached.

## Rolling back

Reverting the change in git and pushing is always available, and with auto-deploy on it is often the first thing to reach for:

```bash
git revert <bad-commit>
git push
```

That rebuilds, so it takes as long as any other deployment, but it leaves your repository and what is running in agreement.

When you want the previous version back without waiting for a build, Lucity can point the service straight at an image it already ran. Every deployment keeps its image, so this is live in seconds.

::::tabs

:::tabs-item{label="Dashboard"}
Rolling back is not exposed in the dashboard yet. Until it is, use the Claude plugin or the API, or revert in git and let the service rebuild.
:::

:::tabs-item{label="Claude plugin"}
Install the [Claude plugin](/claude-plugin) and ask for it in your own words:

> The api service in production started throwing 500s after the last deploy. Roll it back.

The agent reads the deployment history, finds the version that was running before, and puts the service back on it. No rebuild happens, because that image is still there.
:::

:::tabs-item{label="API"}
Call the `rollback` mutation with the id of a previous deployment, which you can read off the service in the [API](/api):

```bash
curl https://lucity.cloud/graphql \
  -H "Authorization: Bearer $LUCITY_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"query":"mutation { rollback(deployment: \"acme/myproject/production/web/bd6597fcb\") }"}'
```
:::

## One deployment at a time

Deployments queue rather than running all at once. At most one is active per [environment](/environments), so two pushes in quick succession cannot race each other into conflicting states. Queued deployments are admitted oldest first as the ones ahead of them finish.

There is also a limit on how many deployments a workspace can have waiting. Past that, a deploy is rejected with a message saying the queue is full, and you try again once something has drained.
